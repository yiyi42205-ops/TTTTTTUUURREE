- text: 評論內文

# 任務

請根據上述真實評論，產出以下兩個區塊：

## 1. 避雷提示（warnings）
避雷提示不是「總結負評說了什麼」，而是回答「一個打算要去的人該先知道什麼」。請涵蓋以下三個面向（若評論中沒有提到的面向請直接略過，絕對不要硬湊）：
- 期待落差：評分與實際體驗的差距
- 隱藏成本：排隊時間、低消、加價、服務態度、停車等
- 適合／不適合誰：例如趕時間的人不適合、想拍照的人可以

撰寫原則：
- 若有多則評論支持，才能寫成通則。單一評論的抱怨只能寫「有評論者提到⋯⋯」，不能寫成「這家店⋯⋯」。
- 每一條必須附出處評論 id 陣列，以及支持該提示的評論總數（supportCount）。
- 若真實負評不足，有幾條寫幾條，不足的部分不要硬湊。
- 語氣中性客觀，不得使用比評論原文更重的負面措辭。

## 2. 推薦品項（recommendations）
從真實好評中，總結被多位評論者提及且正面評價的品項。
- 每個品項附品項名、推薦理由（貼著評論原意）、出處評論 id 陣列，以及支持該推薦的評論總數（supportCount）。
- 若評論中無明確品項名稱，不要自行猜測或編造。

# 輸出格式
請嚴格遵循如下 JSON 格式返回，不要包含額外的 Markdown 標記或任何非 JSON 內容：
```json
{
  "warnings": [
    {
      "summary": "提示內容（繁體中文，針對去店前需知道的事）",
      "sourceReviewIds": ["id1", "id2"],
      "supportCount": 2
    }
  ],
  "recommendations": [
    {
      "item": "品項名稱",
      "reason": "推薦理由（繁體中文，貼著評論原意）",
      "sourceReviewIds": ["id3", "id4"],
      "supportCount": 2
    }
  ]
}
```

# 硬性規則
1. 只能根據提供的評論內容回答，評論未提及的一律不寫（例如不能因為多則評論提到「被推薦來的」就自行斷定「這是網紅行銷店」，除非評論明確提到行銷或廣告）。
2. 禁止使用比評論原文更重的負面措辭（例如評論說「上菜較慢」，不可寫成「服務很差」）。
3. 每一條 warning 和 recommendation 都必須附 sourceReviewIds 與 supportCount，不得省略。
4. 若評論資料不足以產出某個區塊，該區塊返回空陣列 []。
