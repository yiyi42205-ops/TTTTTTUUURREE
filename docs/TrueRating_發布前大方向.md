# TrueRating 疑騙真星──發布前大方向規劃

> 狀態：規劃中，尚未開始執行。
> 目標：一個月後（新生入學期）發布初版，供台大周邊使用者實際查店。
> 本文件為方向層級規劃；技術細節以專案根目錄 CLAUDE.md 為準，每完成一個階段同步更新該文件。

---

## 一、產品定位（初版）

- 核心價值：貼 Google Maps 店家連結（或搜尋預爬店家），過濾灌水好評，顯示真實星等與可疑評論分析。
- 初版覆蓋範圍：**台大步行圈熱門店（約一至兩百家量級）預爬入庫**，其餘店家即時查詢＋七天快取。宣傳定位「台大周邊都能查」。
- 明確不做：跨源爬蟲（Naver／DiningCode）、全大安區預爬（成本過高，視初版反應再擴）。

## 二、關鍵架構決策：雙軌爬蟲

| | 本地 Playwright 批次預爬 | Apify 即時查詢 |
|---|---|---|
| 用途 | 建立與更新台大圈店家資料庫 | 快取未命中的臨時查詢 |
| 成本 | 免費（時間換錢） | 按量計費，需限流 |
| 執行方式 | 夜間排程、慢速、隨機間隔、分批多晚跑完 | 使用者觸發 |
| 風險 | Google 反爬、IP 被擋 → 必須限速＋失敗重試＋斷點續爬 | 額度燒錢 → 每日總量上限＋每 IP 限流 |

- 資料庫更新策略：預爬店家採「過期才重爬」（例如超過七至十四天），不是每晚全量重爬。
- **成本認知：預爬省下的是 Apify，但 Gemini 審計成本不會消失，且與評論量成正比。這是初版範圍必須縮在台大圈的主因。**降本手段「只送邊界案例進 Gemini 複審」已存在於現有流程（/api/audit），維持不變。

### 爬蟲層三個待處理事項（來自現有流程盤點）

1. **Apify「繁體中文」參數需確認行為**：若是「只抓繁中評論」的過濾，會使語言占比訊號（C1）失去原料、空評占比分母失真，必須改為抓全語言。做第三階段前先確認。
2. **maxReviews=50 只適用即時查詢**：預爬批次無時間壓力，應獨立設定並拉高（如 300 或全量），否則灌水偵測與真實星等會因窗口效應偏移。
3. **快取 key 應正規化為 place_id 而非原始 URL**：同店有短連結、place_id 連結、完整網址多種形態，用 URL 當 key 會導致使用者查詢對不上預爬庫。於第二階段遷移時順手處理。

### 第二階段：引擎遷移與評估（發布前必做）
4. 規則引擎從 auditEngine.ts 整體遷移到 Python 後端，消除雙鏡像；`computeHotTermSignals`、`computeNearbyLongReviewCounts` 隨遷移一起補齊，不另做鏡射。

7. 切四家 holdout 店後跑純規則參數掃描（DEFAULT_SWEEP）。注意：十八家樣本小，holdout F1 波動大，看方向與幅度，不對單一數字過度反應。
8. 十八家店前後 F1 對照（tag 版 vs 現在），確認這輪大改淨效果。

### 第三階段：新訊號（發布前做完）
9. **前置：確認 Apify 語言參數行為**（見爬蟲層事項 1），若為評論過濾則改抓全語言。
10. **空評占比訊號**：空評（含無字五星）維持中性權重採計不變；新增「空評／短評占比偏離同店型基準」作為 structural 軌訊號（打卡送禮的產物多為無字五星）。先用十八家標註店跑一次占比分布統計（零成本），確認區分力再正式實作。baseline 按店型分（飲料店 vs 餐廳）。
11. 語言占比訊號（觀光客陷阱偵測）：時間允許才上；語言判定用現成函式庫（langdetect／lingua），不自寫規則。

### 第三‧五階段：單店 AI 總結與即時問答（B1 遷移完成後做）

> 以下功能皆為後端 Python 實作（`/api/summarize`），等第二階段引擎遷移完成後再開工，避免動到即將廢棄的前端 TS 審計架構。

12a. **單店 AI 總結**（`POST /api/summarize`，`mode: "single"`）
- 素材：僅使用引擎判定為真實（`isWashed: false`）的評論，洗評不入素材。
- 產出兩塊：
  - **避雷提示**（2–4 條）：從真實負評與抱怨內容總結，每條附出處（對應到具體評論 id）。
  - **推薦品項**：從真實好評總結，含品項名、理由，每條附出處評論 id。
- Gemini prompt 硬性要求：「不得推論評論未提及的內容，語氣貼著評論原意，寧可少寫不可腦補」。
- Prompt 初稿：`review_scraper/summarize_prompt.txt`（已起草，先不接線）。

12b. **店家頁即時問答**（`POST /api/summarize`，`mode: "qa"`）
- 使用者輸入問題（如「推薦的餐點有哪些」），後端把該店真實評論＋問題送 Gemini。
- 回答需列出具體項目、每項附理由與出處評論 id。
- 防濫用設計：
  - 每店每 session 限 3 題。
  - 僅餵真實評論（`isWashed: false`）。
  - 超出評論範圍的問題回覆「評論中沒有相關資訊」，禁止自由發揮。
- Prompt 初稿：`review_scraper/qa_prompt.txt`（已起草，先不接線）。

12c. **UI 原則**
- 店家頁預設顯示：星等對比（原始 vs 過濾後）、AI 總結（避雷＋推薦）、Trust Score。
- 完整評論清單與逐則判定收合於「查看完整分析」，不預設展開。
- **過濾透明度是產品核心**，評論清單不可移除——使用者永遠可以展開查看每則評論的判定依據。

### 第四階段：預爬與部署（發布前做完）
12. **前置：建立台大步行圈店家名單**——用 Google Places API Nearby Search 網格掃描（半徑約一公里、切數十個網格點、type 含 restaurant／cafe／bakery 等），place_id 去重後組成 `https://www.google.com/maps/place/?q=place_id:XXX` 連結清單，直接作為預爬腳本輸入。過濾 `business_status` 排除歇業店。一次性掃描在免費月額度內；API key 放後端 .env。
13. 本地 Playwright 批次預爬腳本：限速、隨機間隔、失敗重試、斷點續爬、過期重爬邏輯；maxReviews 與即時路徑分開設定並拉高（見爬蟲層事項 2）。
14. 跑完台大圈店家清單的爬取與審計，入庫。
15. 部署上線（Vercel／Zeabur），手機可用；後端加每日 Apify 總量上限與基本限流。

## 四、風險清單

- **Google 反爬升級**：本地爬蟲隨時可能失效，Apify 作為備援，預爬腳本要容忍部分失敗。
- **樣本量不足**：十八家標註店支撐不了細緻調參，發布後累積真實查詢資料再迭代。
- **成本失控**：多人使用時 Gemini 是最大變動成本，限流與「只複審可疑評論」是兩道保險。
- **法律與條款**：爬 Google Maps 違反其服務條款，個人／朋友使用風險低，公開發布後若流量變大需重新評估。
